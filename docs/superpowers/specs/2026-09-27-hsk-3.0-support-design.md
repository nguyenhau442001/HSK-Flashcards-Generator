# HSK 3.0 Support — Design Spec

Date: 2026-09-27

## Background

HSK official exam format switches from 2.0 to 3.0 starting December 2026.
The app currently only models the 2.0 syllabus: 6 levels (HSK1–HSK6,
150/150/300/600/1300/2500 words, 5000 total). HSK 3.0 restructures the
syllabus into 9 levels grouped into 3 bands (Sơ cấp 1–3, Trung cấp 4–6,
Cao cấp 7–9), with different and larger word counts per level.

2.0 and 3.0 are different, non-overlapping syllabi. Existing HSK1–6 data,
progress, and UI must be left untouched — 3.0 is added alongside, not a
replacement.

## Scope

**In scope (this spec, full infra):**
- Data schema and file layout for all 9 HSK 3.0 levels.
- `LEVELS`-equivalent config for 3.0 levels.
- Version switcher UI (2.0 / 3.0) inside the existing "Theo cấp độ" vocab
  sub-tab.
- Progress storage keying for 3.0 levels, isolated from 2.0 keys.
- Level picker cards for all 9 levels, wired into the existing
  select/study/progress flow unmodified.

**In scope (this spec, data population — phased):**
- Phase 1: populate real vocabulary for Sơ cấp only (levels 1–3, ~2245
  words total) using Claude's best-effort synthesis from public knowledge
  of the HSK 3.0 (新汉语水平考试 3.0 / CTI) syllabus.
- Levels 4–9 ship as `available: false` placeholders (empty word arrays)
  until populated in later sessions.

**Explicitly out of scope:**
- Full 11,000-word population for levels 4–9 (separate future work, one
  band at a time, each reviewed before the next).
- Prebuilt TTS audio for 3.0 levels (2.0 pattern of `prebuiltAudioManifest`
  reused as-is; 3.0 levels fall back to Web Speech API like HSK3–6 today).
- Any change to topics, radicals, mini-games, or fast-review — those
  systems key off `LEVELS`/`hskLevelKeys()` and continue working against
  2.0 keys unless explicitly extended later.

## Data Accuracy Caveat

Claude does not have a verified, authoritative export of the HSK 3.0
word lists — synthesis is from training knowledge and any web search
performed at implementation time, not an official CTI/Hanban dataset
file. Phase 1 (Sơ cấp, levels 1–3) is built first specifically so the
user can spot-check accuracy before Claude proceeds to Trung cấp and
Cao cấp. Do not treat Phase 1 output as ground truth until reviewed.

## Data Layout

New directory, parallel to the existing flat files:

```
database/vocabs/hsk3_0/
  level1_vocabularies.json   (approx. 300 words)
  level2_vocabularies.json   (approx. 300 words)
  level3_vocabularies.json   (approx. 300 words)   Phase 1 target: 1–3
  level4_vocabularies.json   (approx. 300 words)   placeholder ([])
  level5_vocabularies.json   (approx. 300 words)   placeholder ([])
  level6_vocabularies.json   (approx. 300 words)   placeholder ([])
  level7_vocabularies.json   (approx. 300 words)   placeholder ([])
  level8_vocabularies.json   (approx. 300 words)   placeholder ([])
  level9_vocabularies.json   (approx. 300 words)   placeholder ([])
```

Exact per-level counts are set from whatever syllabus breakdown Claude
can find/reconstruct at implementation time; the totals above (2245 /
5636 / 11092 across the three bands) are the official approximate band
totals, not a fixed per-level split — actual per-level word counts will
be documented in the level's `total` field in config, derived from the
actual JSON array length once built.

Word object schema is unchanged from the existing files — every entry
has `id`, `hanzi`, `pinyin`, `meaning`, `example_zh`, `example_py`,
`expected_pinyin`, `example_vi`. This keeps `flashcard.js`,
`vocabulary-overview.js`, `speech.js`, etc. working against 3.0 data
with zero code changes to word-rendering logic.

## Config (`assets/js/state.js`)

New sibling config object, not merged into `LEVELS`:

```js
const LEVELS_HSK30 = {
  hsk30_1: { label: 'HSK 3.0 – 1', band: 'Sơ cấp', dataUrl: 'database/vocabs/hsk3_0/level1_vocabularies.json', available: true,  total: <actual count> },
  hsk30_2: { label: 'HSK 3.0 – 2', band: 'Sơ cấp', dataUrl: 'database/vocabs/hsk3_0/level2_vocabularies.json', available: true,  total: <actual count> },
  hsk30_3: { label: 'HSK 3.0 – 3', band: 'Sơ cấp', dataUrl: 'database/vocabs/hsk3_0/level3_vocabularies.json', available: true,  total: <actual count> },
  hsk30_4: { label: 'HSK 3.0 – 4', band: 'Trung cấp', dataUrl: 'database/vocabs/hsk3_0/level4_vocabularies.json', available: false, total: 0 },
  hsk30_5: { label: 'HSK 3.0 – 5', band: 'Trung cấp', dataUrl: 'database/vocabs/hsk3_0/level5_vocabularies.json', available: false, total: 0 },
  hsk30_6: { label: 'HSK 3.0 – 6', band: 'Trung cấp', dataUrl: 'database/vocabs/hsk3_0/level6_vocabularies.json', available: false, total: 0 },
  hsk30_7: { label: 'HSK 3.0 – 7', band: 'Cao cấp', dataUrl: 'database/vocabs/hsk3_0/level7_vocabularies.json', available: false, total: 0 },
  hsk30_8: { label: 'HSK 3.0 – 8', band: 'Cao cấp', dataUrl: 'database/vocabs/hsk3_0/level8_vocabularies.json', available: false, total: 0 },
  hsk30_9: { label: 'HSK 3.0 – 9', band: 'Cao cấp', dataUrl: 'database/vocabs/hsk3_0/level9_vocabularies.json', available: false, total: 0 },
};
Object.assign(LEVELS, LEVELS_HSK30);
```

Keys are merged into the single `LEVELS` object (same pattern already
used for `TOPICS`), so every existing `LEVELS[currentLevel]` lookup in
`flashcard.js`, `speech.js`, `levels.js`, `backup.js`, `progress.js`
keeps working unmodified for 3.0 levels too — no `if (isHsk30)` branches
needed in card/study/progress/backup code.

`hskLevelKeys()` currently excludes `TOPICS` keys only. It must also
exclude `LEVELS_HSK30` keys, since it drives the 2.0-only learning
dashboard aggregate (`learningProgressSummary` in `levels.js`). A
`hsk30LevelKeys()` counterpart is added for the 3.0 dashboard/picker.
Alternative considered: one combined `hskLevelKeys()` that includes both
and tags entries with `version` — rejected because the dashboard's
"today's goal" / "quick start" logic is meant to track one syllabus at a
time per the approved version-switcher UX, and mixing both would produce
a nonsensical combined progress bar.

Each `LEVELS` entry gains a `version: '2.0' | '3.0'` field (added to
existing HSK1–6 entries too, defaulted `'2.0'`) so shared code (backup
restore, overview) can label which syllabus a card belongs to without
relying on key prefix string-matching.

## Storage Keys

`storageKey()` in `state.js` builds `hsk_<currentLevel>_<suffix>_v2`.
Since 3.0 keys are `hsk30_1`..`hsk30_9` (distinct from `hsk1`..`hsk6`),
resulting storage keys (`hsk_hsk30_1_progress_v2`, etc.) never collide
with existing 2.0 keys. No migration needed; this is purely additive.

`LAST_LEVEL_KEY` (`hsk_last_level_v1`) is shared globally across
versions today. Left as-is: whichever level (2.0 or 3.0) was last
opened is what "quick start" resumes, which is reasonable single-user
behavior and avoids adding a second last-level slot for a first version.

## UI

**Version switcher** — inside the existing "Theo cấp độ" sub-tab
(`screenPicker`), above the level grid: two small toggle buttons "HSK
2.0" / "HSK 3.0", same visual pattern as `vocabSubTabLevel`/`Topic`.
New JS state `pickerVersion` ('2.0' default), new function
`setPickerVersion(version)` that toggles which level-grid block is
visible and re-renders progress bars for that block.

Two level-grid blocks live in `screenPicker`: the existing 6-card grid
(id `levelGrid20`, wraps the current hardcoded HSK1–6 cards unchanged)
and a new 9-card grid (id `levelGrid30`, cards `hsk30_1`..`hsk30_9`,
grouped visually into Sơ/Trung/Cao cấp sub-headers using the `band`
config field). Cards for `available:false` levels (4–9 initially) render
with a "Sắp có" (coming soon) badge and are non-clickable, following the
same disabled-card treatment already used elsewhere for unavailable
levels — confirm `LEVELS[level].available` gating exists in
`selectLevel`/card click handler and reuse it as-is.

Cards are still hand-authored HTML (matching the existing un-templated
6-card block) rather than JS-rendered from `LEVELS_HSK30`, to keep the
change mechanically consistent with the current file and avoid
introducing a new templating pattern for one feature.

`renderLevelProgress()` in `levels.js` already iterates
`Object.keys(LEVELS)`, so it will automatically pick up and paint
mastery bars for the new `hsk30_*` cards with zero changes.

`learningProgressSummary()` / `renderLearningDashboard()` continue to
use `hskLevelKeys()` (2.0 only) so the homepage daily-goal dashboard
stays scoped to whichever syllabus is primary; no dual-dashboard is
built in this phase.

## Testing

- `python3 -m http.server 8000`, load `flashcards.html`, verify:
  - Existing HSK1–6 cards and progress render unchanged (regression
    check — no visual/behavioral diff).
  - Version switcher toggles between 2.0 and 3.0 grids.
  - HSK 3.0 levels 1–3 open, render flashcards correctly, pinyin/speech/
    example sentences work, progress saves and persists across reload
    under `hsk_hsk30_1_progress_v2` etc.
  - Levels 4–9 show disabled/"coming soon" and are not selectable.
  - Backup/restore JSON export includes 3.0 progress and round-trips.
- `git diff --check` for whitespace issues.
- No build/typecheck tooling in this repo (static JS); manual browser
  verification is the verification step.
